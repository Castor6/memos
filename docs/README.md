## 记录维护方式

- 助手负责把讨论中的需求、验收标准和关键取舍整理成记录，完成后补充实际结果。
- 任务详情按需检索，不要求每次启动读取全部历史。知道任务编号时直接打开对应文件。
- `tasks/INDEX.md` 只保留固定检索说明，不登记任务列表；按文件名、标题、模块和正文关键词搜索。
- 任务使用 `TASK-YYYYMMDD-短主题` 编号，文件名保持稳定；详情是带日期的工作事实，不是实时看板。历史记录以其中的验证日期为准。
- 只记录本次实际实现、验证结果和未覆盖范围。不设置依赖外部变化的 CI、合并或部署状态字段；后续进展通过关联 PR、Actions、Release 或私有运维记录查询。已发生的外部操作可带日期和证据作为历史事实保留。
- 单个任务文件由一个会话负责维护，在文件中注明维护会话或工作分支；交接后可以续写。其他会话独立开展的工作另建记录并互链，避免共同维护大任务进度表；代码改动使用独立 worktree。
- 收尾只更新本次任务，核对链接和验证边界，不修改总索引。保留关键决定与实际结果，不逐次记录推送、等待 CI 或索引冲突，不重复 Git/PR 流水。
- 保留现有历史文件，无需为此次规则调整重新归档。若需浏览总目录，可按需在本地生成，生成结果不提交 Git。
- 重要的长期要求应提炼到协作规则或模块文档，并链接原任务，避免埋在历史记录中。
- 原始聊天、整段日志、测试数据库、账号会话和截图默认留在被 Git 忽略的本地目录；任务文档记录精简结果和复现步骤。
- 源码和通用方案随 Git 维护。真实部署地址、凭据、笔记、备份及运维详情继续放在独立的私有维护目录。
